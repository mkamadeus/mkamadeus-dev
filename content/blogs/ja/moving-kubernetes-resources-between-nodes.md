## 背景

仕事で新しいKubernetesクラスターをプロビジョニングしました。
AWS Elastic Kubernetes Serviceと提供されたテンプレートを使用して、必要なアプリケーションでクラスターを比較的迅速にプロビジョニングし、セットアップできます。
しかし、設定が間違っていることに気づきました。特に、ノードの1つが適切に設定されていませんでした。
すでにオートスケーリング、災害復旧などのアプリケーションをセットアップしていました。
進捗をリセットする代わりに、インストールされたアプリケーションを保持したいと思いました。

## 手順

TLDR; ノードから別のノードにリソースを移動する手順は次のとおりです：

1. 一時的なワーカーノードをプロビジョニングします。
2. 壊れたノードと一時的なワーカーノード以外のすべてのノードをコードンします。
3. 壊れたノードをドレインして、リソースを一時的なノードに移動します。
4. 正しいパラメータで壊れたノードを再プロビジョニングします。
5. 一時的なノードをコードンして、リソースを修正されたノードに移動します。
6. 他のノードのコードンを解除します。

> この手順は柔軟で、ノードの再プロビジョニングのさまざまなケースに適応できます。

## 説明

### 一時的なノードのプロビジョニング

ノードがすでにプロビジョニングされているため、Kubernetesは単独で問題を修正することはできません。
したがって、リソースを一時的にここに移動するために、この一時的なノードを追加する必要があります。
システムによって異なる場合があるため、自分のシステムで行うのと同じようにノードをプロビジョニングしてください。

### ノードのコードン

ノードのコードンは、ノードをスケジュール不可としてマークすることです。
これは、そこにすでにスケジュールされているリソースには適用されません。
リソースが望ましくないノードに移動することを避けるためにこれを行います。
私は`k9s`を使用していますが、`kubectl`でも同じことができます。

```sh
kubectl get nodes
kubectl cordon NODE
```

### ノードのドレイン

ドレインは、追加のステップを伴うコードンです。これは、リソースを「ドレイン」する、つまり別のノードに移動することです。
ノードをスケジュール不可としてマーク（コードン）した後、リソースは利用可能なノードに移動されます。
一時的なノード以外のノードをコードンした場合、一時的なノードに移動するはずです。

```sh
kubectl get nodes
kubectl drain NODE
```

### ノードの再プロビジョニング

私の場合、間違ったサブネットでノードをプロビジョニングしました。
再プロビジョニング以外にこのノードを修正する方法はないため、ノードのコードンとドレインを行うことになりました。
ノードを再プロビジョニングする必要がない場合、これらのステップは関係ありません。

### ノードのアンコードン

名前が示すように、これはノードのコードンの反対です。
このステップは、移行プロセスを完了した後、ノードを再びスケジュール可能にします。

```sh
kubectl get nodes
kubectl uncordon NODE
```

## 結論

これらのステップに従って、壊れたノードを更新できます。
これらのステップは、壊れたノードを更新するための一般的なフレームワークも提供します。
